This blog introduces how to migrate and enable dynamic resource allocation feature for KubeEdge cluster.

# Why we want to use DRA Feature?

Although KubeEdge provide the DMI(device managerment interface) to control and manager edge side devices, but with the following reason, we still need to enable this feature of DRA with KubeEdge
- DRA introduces a **cloud-native**, **flexible allocation model** patterned after how Kubernetes handles persistent storage.
It replaces the traditional device plugins, which is extremely limited while working. 
- More and more hardware like GPU start to support DRA feature now.
- DRA is becoming the standard and critira with Kubernetes cluster       

## Dynamic GPU Slicing

The Old Way: A pod requested an entire GPU. If an application only needed 10% of that GPU's processing power, the remaining 90% sat idle and wasted, as other pods couldn't touch it.

With DRA: Pods can request specific slices, memory limits, or time-sharing channels on a device. You can pack multiple lightweight machine learning inference pods onto a single physical GPU node safely, drastically reducing infrastructure costs.

## Complex Multi-Device Arbitrary Claims

The Old Way: If a pod needed two specific types of GPUs connected by a high-speed NVLink bridge, the scheduler couldn't easily verify the network topology. It would randomly assign any two GPUs, often hurting performance.

With DRA: The allocation model allows drivers to evaluate hardware topologies during scheduling. DRA can ensure that a distributed training pod gets a tightly coupled cluster of GPUs that can talk to each other at maximum speed.

## Network-Attached and Remote Discovered Hardware

The Old Way: Device plugins only understood hardware physically plugged into the PCIe slots of that exact node.

With DRA: The system can allocate network-attached hardware (like a pool of AI chips sitting on a remote server accessible via RDMA fabrics). DRA claims the resource over the network network socket line, attaches it to the pod, and releases it back to the cluster pool when done.

## Clean Initialization & Teardown Lifecycles

The Old Way: Pre-start container hooks were brittle. If a pod crashed unexpectedly, hardware memory states could get corrupted or "stuck" in a zombie reservation state.

With DRA: DRA relies on explicit, robust ResourceClaims. Hardware initialization happens before the container sandbox boots, and the state is explicitly torn down when the pod is deleted, preventing resource leakage.

# How to Migrate and Enable DRA for KubeEdge?

Although DRA is mature in Kubernetes, KubeEdge `v1.23` still aligns to Kubernetes main stream `v1.32`, where DRA APIs version is still `v1beta1`. Thus we choose that DRA  `v1beta1` version as baseline. And porting entire DRA API version `v1`(available with Kubernetes v1.35) to Kubeedge v1.23 is out of scope of this manual.

An update of the procedure will be expected when newer k8s is bumped into KubeEdge.
