## Device Method API Introduction

From the traditional definition of a physical model, the parameters of a device are usually divided into three categories according to their functional type:

- **Property** : Used to describe the device status, such as the ambient temperature read by the temperature sensor, the on/off status of the socket, etc.

- **Method** : A method of the device that can be called and executed externally, such as adjusting device parameters.

- **Event** : Describes an event reported by the device to the cloud.

In the first article of this series, we introduced the definition of device properties in the v1beta1 version of the device management API, allowing users to obtain the status of devices. In KubeEdge version 1.19, we further extended the API by introducing device methods, allowing users to call device methods to achieve dynamic control over device properties.

The API definition for Device Method is as follows:

```yaml
// DeviceMethod describes the specifics all the methods of the device.
type DeviceMethod struct {
    // Required: The device method name to be accessed. It must be unique.
    Name string `json:"name,omitempty"`
    // Define the description of device method.
    // +optional
    Description string `json:"description,omitempty"`
    // PropertyNames are list of device properties that device methods can control.
    // Required: A device method can control multiple device properties.
    PropertyNames []string `json:"propertyNames,omitempty"`
}
```
The Device Method is designed to consist of the following three core fields :

   **Name :** Used to identify the device method. Within the same device instance  , the name of each method must be unique.

   **Description:** Used to explain the specific purpose of this method.

   **PropertyNames :** Defines the list of device properties that this method can operate on. A method can control multiple device properties.

Below is a  sample device-instance  configuration file demonstrating how to add a Device Method:
```yaml
apiVersion: devices.kubeedge.io/v1beta1
kind: Device
metadata:
  name: sensor-tag-instance-02
  namespace: default
spec:
  deviceModelRef:
    name: sensor-tag-model
  nodeName: edge-node
  properties:
    - name: temperature
      visitors:
     ...
  methods:
    - name: setValue
     description: This method aim to writing values to device properties
     propertyNames:
       - temperature
       - name2
```
Here we define a  setValue method for  the sensor-tag-instance-02 device  , which allows users to modify  the values   of the two device attributes, temperature  and  name2  .

It is important to note that   the Device Method defined in the device-instance configuration file is only a framework definition of the method; the specific functional implementation still needs to be completed in the mapper device driver layer.

## Mapper-Framework Device data write interface

After defining the device method framework through the Device Method API , users need to implement the corresponding data writing logic in the mapper device driver layer based on the predefined methods. To simplify user operations, Mapper-Framework version 1.19 implements the device writing interface:
```yaml
func (c *CustomizedClient) DeviceDataWrite(visitor *VisitorConfig, deviceMethodName string, propertyName string, data interface{}) error {
    // TODO: add the code to write device's data
    // you can use c.ProtocolConfig and visitor
    return nil
}
```
Specifically, users can call  the device protocol configuration information (ProtocolConfig) and device attribute access configuration (VisitorConfig) in  the device-instance CRD to perform write operations on device registers. For example, in a Modbus device, users can access a specific Modbus register address according to VisitorConfig  and write new values, thereby controlling the device's operating status.

##   Mapper-Framework Restful API capability enhancement

In KubeEdge version 1.19, the Mapper-Framework has extended the RESTful API, making it easier for users to query and call Device Methods. Specific features are as follows:

  Methods to obtain all device information
```yaml
Url: https://{mapper-pod-ip}:{mapper-api-port}/api/v1/devicemethod/{deviceNamespace}/{deviceName}
Response:
{
"Data": {
     "Methods": [
         {
             "Name": "setValue",
             "Path": "/api/v1/devicemethod/default/random-instance-01/setValue/{propertyName}/{data}",
             "Parameters": [
                 {
                     "PropertyName": "random-int",
                     "ValueType": "int"
                 }
             ]
         }
     ]
 }
 }
```

The  response  indicates that the target device has a Device Method named `setValue`, which can be invoked using the fields shown in the Path. Furthermore, the `setValue` method can be used to control the ` random-int` device attribute.

   Create a device data write request

```yaml
Url: https://{mapper-pod-ip}:{mapper-api-port}/api/v1/devicemethod/{deviceNamespace}/{deviceName}/{deviceMethodName}/{propertyName}/{data}
Response:
 {
 "statusCode": 200,
 "Message": "Write data ** to device ** successfully."
 }
```
There are two ways for users to initiate device data write requests via the RESTful API :

**1) Edge-end call**

Users can directly interact with devices by sending requests through the RESTful API exposed by the Mapper Pod on the edge node, achieving low-latency local control.

**2) Cloud access**

In the cloud, users can use components such as EdgeMesh to forward requests from the cloud to the corresponding edge nodes, where Mappers will process and execute device write operations.

Regardless of the invocation method used, the Mapper will perform the following operations upon receiving a device data write request:

- Parse the request content to obtain the target device, target method, and its parameters.

- The DeviceDataWrite function in the device driver layer is invoked to communicate with the device according to the defined protocol.

- Complete writing device attributes and update device status.
