With the rapid arrival of the era of the Internet of Things, the widespread adoption of 5G networks has led to a rapid increase in the amount of data generated by edge devices. Ordinary edge devices lack sufficient computing power, so traditional methods centralize edge data to cloud data centers for processing, which can easily pose challenges to real-time response, network stability, and data security.

To meet users' higher availability requirements in large-scale device scenarios, KubeEdge Device-IoT introduced the Device Management Interface (DMI) in version 1.12. DMI integrates device management interfaces, decouples management plane and business plane data, optimizes device management capabilities in edge computing scenarios, and creates a device digital twin management platform based on cloud-native technology.

In version 1.15, we iteratively updated the device management API of version v1beta1 based on user needs for edge device management, and improved the DMI data plane functionality on this basis, which is carried out in the southbound Mapper development framework Mapper-Framework. Mapper-Framework provides a brand-new automatic Mapper generation framework, integrating DMI device management plane and data plane capabilities. It can automatically generate Mapper projects; users only need to implement the device driver functionality to use the Mapper to manage edge devices, simplifying the complexity of Mapper design and development and improving development efficiency. Regarding the updates in the `Device-IoT` field in this new version, we plan to release a series of articles to introduce these features in detail. The general outline of the articles is as follows:

 ## Device Management API Based on Object Model

To meet user needs, in version v1.15.0, KubeEdge SIG Device-IoT introduced a device management API based on a physical model, upgrading Device Model and Device Instance from version v1alpha2 to v1beta1. The new version of the device management API provides a more comprehensive description of physical devices, adds fields related to edge device data processing, and is compatible with enhanced DMI data plane capabilities. The northbound device API, combined with the southbound DMI interface, enables device management and device data processing. Key API updates include:
### 1. Device Model

The Device Model is used to describe the common device attributes of a class of edge devices. According to the definition of the object model, the Device Model adds fields such as device attribute description, device attribute type, device attribute value range, and device attribute unit, as shown in the following figure:
```yaml
// ModelProperty describes an individual device property / attribute like temperature / humidity etc.
type ModelProperty struct {
    // Required: The device property name.
    // Note: If you need to use the built-in stream data processing function, you need to define Name as saveFrame or saveVideo
    Name string `json:"name,omitempty"`
    // The device property description.
    // +optional
    Description string `json:"description,omitempty"`
    // Required: Type of device property, ENUM: INT,FLOAT,DOUBLE,STRING,BOOLEAN,BYTES,STREAM
    Type PropertyType `json:"type,omitempty"`
    // Required: Access mode of property, ReadWrite or ReadOnly.
    AccessMode PropertyAccessMode `json:"accessMode,omitempty"`
    // +optional
    Minimum string `json:"minimum,omitempty"`
    // +optional
    Maximum string `json:"maximum,omitempty"`
    // The unit of the property
    // +optional
    Unit string `json:"unit,omitempty"`
}
```
The image above shows the core `ModelProperty` field of the Device Model. The Typefield defines the data type of the property, and `AccessMode` defines the access mode, including read-write and read-only. When the access mode is set to read-only, the Mapper directly returns the collected device data; conversely, when set to read-write, the Mapper performs normalization and other processing on the collected device data before returning it. Minimum and Maximum define the maximum and minimum values of the device property, and the Unit field defines the unit of the device property. The image below shows an example of a Device Model configuration file:
```yaml
apiVersion: devices.kubeedge.io/v1beta1
kind: DeviceModel
metadata:
  name: beta1-model
spec:
  properties:
    - name: temp                      # define device property
      description: beta1-model
      type: INT                       # date type of device property
      accessMode: ReadWrite
      maximum: "100"                  # range of device property (optional)
      minimum: "1"
      unit: "Celsius"                 # unit of device property
  protocol: modbus                    # protocol for device, need to be same with device instance
```

### 2. Device Instance

A Device Instance represents an actual device object. In version v1beta1, all built-in protocol configurations within a Device Instance, including Modbus, OPC-UA, and Bluetooth, have been removed. Users can configure device protocols through extensible Protocol configurations, enabling device access using any protocol. Mappers for built-in protocols such as Modbus, OPC-UA, and Bluetooth will remain in the Mappers-go repository, and built-in Mappers for other protocols will be continuously added.
```yaml
type ProtocolConfig struct {
    // Unique protocol name
    // Required.
    ProtocolName string `json:"protocolName,omitempty"`
    // Any config data
    // +optional
    // +kubebuilder:validation:XPreserveUnknownFields
    ConfigData *CustomizedValue `json:"configData,omitempty"`
}

type CustomizedValue struct {
    Data map[string]interface{} `json:"-"`
}
```

In addition, to enhance the DMI data plane functionality, this update adds device data processing configurations to the device properties of the Device Instance, such as device reporting frequency, data push frequency, whether attributes are reported to the cloud, and device data push method, as shown in the figure below.
```yaml
type DeviceProperty struct {
    ... 
    // Define how frequent mapper will report the value.
    // +optional
    ReportCycle int64 `json:"reportCycle,omitempty"`
    // Define how frequent mapper will collect from device.
    // +optional
    CollectCycle int64 `json:"collectCycle,omitempty"`
    // whether be reported to the cloud
    ReportToCloud bool `json:"reportToCloud,omitempty"`
    // PushMethod represents the protocol used to push data,
    // please ensure that the mapper can access the destination address.
    // +optional
    PushMethod *PushMethod `json:"pushMethod,omitempty"`
}
```
- **ReportCycle** field defines the frequency at which the Mapper pushes data to the user database and user application ;  
- **CollectCycle** field defines the frequency at which the Mapper reports data to the cloud;
- **ReportToCloud** field defines whether the device data collected by the Mapper needs to be reported to the cloud;
- **PushMethod** field defines how the Mapper pushes data to the device.

Currently, it offers data push to user applications via HTTP, MQTT, and OpenTelemetry, and integrates InfluxDB, MySQL, Redis, and TDengine databases. Users can control the Mapper to push device data to user applications and user databases on a scheduled basis through configuration files, and can also actively pull device data through APIs, thus diversifying the device data processing methods. Compared to the traditional method of pushing all data to the cloud for processing, it can effectively reduce the risk of cloud-edge communication congestion.

The following image shows an example of a Device Instance configuration file:
```yaml
apiVersion: devices.kubeedge.io/v1beta1
kind: Device
...
spec:
  properties:
    - name: temp
      collectCycle: 2000      # The frequency of reporting data to cloud, 2 seconds
      reportCycle: 2000       # The frequency of data push to user applications or databases, 2 seconds
      reportToCloud: true     # Decide whether device data needs to be pushed to the cloud
      pushMethod:
        mqtt:                 # Define the MQTT config to push device data to user app
          address: tcp://127.0.0.1:1883
          topic: temp
          qos: 0
          retained: false
      visitors:               # Define the configuration required by the mapper to access device properties (e.g. register address)
        protocolName: modbus
        configData:
          register: "HoldingRegister"
          offset: 2
          limit: 1
  protocol:                   # Device protocol. The relevant configuration of the modbus protocol is defined in the example.
    protocolName: modbus
    configData:
      serialPort: '/dev/ttyS0'
      baudRate: 9600
```
